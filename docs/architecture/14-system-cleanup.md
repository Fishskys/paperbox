# 系统清理

清理保留策略由 `CLEANUP_*` 环境变量加载，新增自动历史清理默认关闭。原有上传 GC 的开关和重试保护不受影响。普通缓存不包含元数据来源、字段历史及人工决定。

`cleanup_candidates` 保存每次扫描的固定候选及版本、保护原因和逐项结果；不能在应用时重新执行会扩大的查询。`cleanup_receipts` 独立于任务和论文保存轻量请求回执，报告裁剪或论文永久删除不能让旧请求重新执行。`managed_search_indices` 按物理索引 UUID 与集群 UUID 登记管理员认领的索引，不凭名字或版本后缀获得删除权。`cleanup_locks` 用于协调清理与应用管理的索引迁移。

永久删除仅接受至多 100 篇显式论文 ID；索引删除仅接受至多 20 个显式物理索引名，两者不与普通缓存混合执行。应用必须引用有效预览；预览期间的变化项跳过并报告，不扩大候选。

部署使用原生文件日志时可配置 `LOG_FILE`，`LOG_MAX_BYTES` 和 `LOG_BACKUP_COUNT` 限制轮转；容器 stdout 由容器日志驱动管理。当前活跃日志不能作为普通文件直接删除。

同一轮转文件由单个 API 进程持有；不要让并行运维脚本或多个实例共用该文件。可仅在启动 API 的进程环境设置 `LOG_FILE`，或为其它进程使用独立文件；多实例部署使用进程管理器或容器的日志收集。

## 管理接口

所有 `/api/admin/cleanup/**` 路径要求管理员权限。`GET /policy` 返回当前配置、上传 GC 和清理调度器状态；`GET /deleted-papers` 分页列出软删论文；`GET /indices` 列出论文索引的归属、别名与回滚保护，`POST /indices/claim` 明确登记物理索引身份。

`POST /jobs` 使用客户端 `request_id` 幂等提交后台任务。`operation=inventory` 始终只读；`operation=cleanup,dry_run=true` 生成固定预览。执行请求使用相同范围、`dry_run=false` 与 `preview_job_id`。预览默认有效 24 小时，配置变化使预览失效。永久删除和索引淘汰不能与其它类别混合。一般任务接口不向非管理员展示清理任务，MCP 的普通任务查询不承载清理报告。

任务详情、列表、按请求编号恢复分别使用 `GET /jobs/{job_id}`、`GET /jobs`、`GET /jobs/requests/{request_id}`；`GET /jobs/{job_id}/report` 分页读取候选，`GET /jobs/{job_id}/download` 下载完整的有界报告。每类默认最多 100 个可清理项及 20 个保护示例，达到上限明确标记 `limited`。数据库记录不估算可归还磁盘字节，不把未知大小显示为零。

无引用字典在 SQL 中先排除被引用项，再进入扫描窗口，避免已使用的作者或期刊会议挡住窗口外的垃圾。候选批次上限允许分批预览；底层存储扫描触及 `CLEANUP_SCAN_LIMIT` 则标记受限并报告失败，不允许用不完整的扫描授权删除，需缩小范围或调整扫描上限。

执行前重新核对记录版本、对象 ETag 与生成时间、索引 UUID 和使用状态。发生变化的候选跳过；外部存储失败逐项记录，任务失败后可通过 `retry_job_id` 只重试尚未完成的候选。进程重启不会自动重放已开始执行的任务。任务详情被裁剪后返回 410，保留的轻量回执阻止旧请求重新执行。

既有元数据和重索引维护任务同样保留独立回执；其写入预览沿用 `CLEANUP_PREVIEW_HOURS` 有效期，过期必须重新预览。

## 数据边界

普通类别包括 `app_logs`、`search_logs`、`jobs`、`parse_cache`、`figure_history`、`orphan_objects`、`orphan_records`。解析缓存仅覆盖 `papers/{paper_id}/extracted/parsed/`，不删除原 PDF 或当前结构化正文。图片历史仅包含非当前、已结束且失效对象已清空的批次。无引用字典记录删除前再次检查引用；当前或活动任务使用的记录、对象受保护。

永久删除仅处理软删论文，沿数据库外键计算完整关联范围，覆盖图片、来源复核和字段决定等表，并清除已登记索引中的论文文档和记录过的对象桶。发现未登记索引仍持有论文文档时保护该论文，要求先检查并登记归属。删除索引本身另需无任何别名、无回滚保护且存在另一份已登记的回滚索引。启用或暂停版本控制的对象桶不按普通对象删除，以免删除标记被误报为空间回收。

`LOG_FILE` 只能位于 `logs/app/` 的直接子文件；清理器保护符号链接、打开中的日志及无法核实身份的文件。应用与 WebUI 容器日志均使用 50 MiB、5 份的轮转声明；宿主机重定向 stdout 由部署方负责轮转。

清理调度器定期重试已标记失效的图片对象。`CLEANUP_AUTO_ENABLED=true` 才启用普通历史保留清理，自动范围限定为应用日志、检索记录、终态任务、空图片历史及无引用字典。解析缓存、孤立对象、论文永久删除和索引淘汰均需手动预览。原有上传 GC 独立运行。

容器镜像与构建缓存、uv/npm/模型缓存、MinIO 未完成的分段上传、数据库 VACUUM/WAL、备份和未登记产物属于外部运维范围。网页只显示其管理边界，不接受任意路径删除、容器 prune 或强制数据库压缩。来源历史与幂等回执有意保留，会随业务增长；数据库 DELETE 回收为可复用页，不保证立即缩小数据文件。

由 systemd 接管的 stdout/stderr 属于宿主机 journald，其空间配额与保留期限由宿主机配置管理，不受 `CLEANUP_LOG_DAYS` 控制。调整共享 journal 的 `SystemMaxUse` 或 `MaxRetentionSec` 会影响其它服务，不能作为 Paperbox 网页的单项目清理操作。

## 运维入口

`scripts/cleanup.py --paper-id UUID` 为显式 ID 生成预览；可重复参数或使用 `--deleted-before ISO时间`，单次范围必须在 1 至 100 篇内。`--apply-preview JOB_ID` 执行已保存的范围；`--retry-job JOB_ID` 续做失败执行。脚本复用同一服务、回执和资源检查，`--request-id UUID` 可恢复结果不明确的提交。旧 `scripts/purge_deleted.py --hard` 无预览执行已禁用。

`scripts/create_index.py` 使用同一清理锁协调别名切换，并登记用户明确指定的目标索引；迁移成功后把旧索引登记为回滚保护。已有索引不会按名称自动认领，管理员应先检查归属再通过管理接口登记。

`uv run python scripts/acceptance_cleanup.py` 使用全新数据库、对象桶和两份索引验证数据库外键、原文删除、历史副本、索引淘汰和别名保护。脚本需要建库权限，结束或失败时只删除本次创建的资源，不删除既有语料。索引清理前还会比对记录的 UUID。
